## Section Summaries

### 1. 去年 12 月，有什么东西变了
- Karpathy 说，过去一年他一直在用 Cursor 这类 agentic 工具，但真正的断点出现在去年 12 月。
- 在那之前，模型写出来的代码块有时能用、有时会错，需要人类不断修补；到了那次迭代之后，他开始频繁遇到“代码块直接就对了”的情况。
- 关键不是一次 demo，而是信任阈值被连续跨过：他反复测试之后发现，自己已经记不清上次改错是什么时候，于是开始真正进入 vibe coding。
- 他还指出，大量人对 AI 的理解还停留在“ChatGPT 平替”阶段，但在 agentic 连贯工作流上，事情已经从根本上变了。

### 2. Software 3.0：提示词就是编程

#### 三代软件范式
- Software 1.0 是传统写代码。
- Software 2.0 是通过整理数据集、训练神经网络来“编程”。
- Software 3.0 则把提示词和上下文窗口里的内容，变成操控 LLM 这个解释器的主要杠杆。

#### 例子 1：Claude Code 安装方式
- Karpathy 用 Claude Code 的安装方式举例：传统思路会写 shell 脚本，再为不同平台不断打补丁，最后脚本越来越臃肿。
- Software 3.0 的做法则是复制一段文字交给 agent，让它自己观察环境、执行操作、在循环里 debug，安装逻辑从“精确控制每一步”变成“给出足够上下文与目标”。

#### 例子 2：MenuGen 被新范式淘汰
- 他自己曾 vibe coding 做过一个 MenuGen 应用：拍餐厅菜单、OCR 识别菜名、调用图像生成器给每个菜配图、再重新渲染菜单。
- 后来他看到 Gemini 直接接收菜单照片，再调用 Imagen 把菜品图片直接覆盖回原图，输出就是一张已经配好图的菜单。
- 这让他意识到，很多“中间应用层”只是旧范式下的必要物，新范式里神经网络会直接吞掉更多流程。

### 3. 为什么 AI 这么锯齿状
- Karpathy 用“可验证性”解释 LLM 的参差不齐：传统计算机擅长做能被明确编码的任务，而当前大模型更擅长做“结果可验证”的任务，因为训练时能获得更清晰的奖励信号。
- 这解释了为什么模型在数学和代码上能力暴涨，但在一些难以验证、缺少训练强化的生活常识问题上仍可能表现荒诞。
- 他给出的对照非常鲜明：像 Opus 4.7 这样的模型可以重构 10 万行代码库、发现零日漏洞，但如果你问它“洗车店 50 米远，我该开车还是走路”，它可能会认真建议你走路。
- 他还用国际象棋举例：GPT-3.5 到 GPT-4 棋力提升，并不一定代表整体智能跃迁，更可能只是因为实验室往预训练集中喂了大量棋局数据。
- 结论很实际：你拿到的是一个没有说明书的系统，得自己去探索它的 RL 电路在哪些问题上真正点亮；如果你的应用场景不在那条电路里，可能就得靠微调或系统设计补足。

### 4. Vibe Coding 和 Agentic Engineering 不是一回事
- 这是全文最重要的区分。Karpathy 认为 vibe coding 的作用是抬高所有人的下限，让更多人能做成原本做不成的软件。
- 但 agentic engineering 的目标完全不同：在不降低原有专业质量标准的前提下提速，你不能因为“是 agent 写的”就容忍安全漏洞、脆弱抽象或质量滑坡。
- 他把这些 agent 形容成“尖刺状、脆弱、带随机性，但极其强大”的实体，工程问题不是能不能让它们干活，而是如何在保持质量边界时组织它们加速。
- 也因此，他认为“10x 工程师”的旧说法已经太小了，真正优秀的 agentic engineer 获得的加速幅度会远超这个量级。

### 5. 真正变贵的人类技能

#### 味觉与判断力
- Karpathy 认为，agent 时代最值钱的人类能力不是 API 细节记忆，而是 taste、judgment 和审慎监督。
- 他用 MenuGen 的一个 bug 举例：用户用 Google 邮箱注册、用 Stripe 另一个邮箱买积分，agent 却试图用 email 字段把两套身份硬连起来，导致积分归属错误。
- 这类错误的本质不是语法问题，而是建模判断问题：涉及资金归属时，为什么会选 email 而不是固定用户 ID？

#### 理解不能被完全代理
- 他还提到自己在简化 micrograd 训练流程时，不断要求模型“再简化一点”，但模型做不到，那种感觉就像明显已经出了 RL 电路范围。
- 他承认自己已经不想记住 PyTorch 里 `reshape` 和 `permute` 的区别，因为这些细节可以外包给 agent；但他仍强调，tensor 的 storage、view、独立内存这些底层概念必须自己理解，否则你无法判断系统为什么高效或低效。
- 对 agent 生成代码的担忧也很具体：代码经常能跑，但容易臃肿、复制粘贴、抽象脆弱。

### 6. LLM 是鬼魂，不是动物
- Karpathy 过去写过一篇文章，把 LLM 比作“鬼魂”而不是“动物”。
- 他的重点不是制造神秘感，而是建立更准确的使用心智模型：动物有内在动机、好奇心和进化出来的驱动力，LLM 没有。
- 它更像由预训练统计电路和后续 RL 叠起来的实体，所以你冲它大吼、拿情绪激励它，并不会像对待动物那样改变它的表现。
- 这个框架的价值在于帮助使用者保持警惕，知道什么方法可能有效、什么方法只是人格化错觉。

### 7. 你可以外包思考，但无法外包理解
- Karpathy 引用过一句他反复回想的话：你可以外包你的思考，但你无法外包你的理解。
- 他的意思不是 agent 没用，而是整个系统仍然需要一个知道“我们为什么做这件事、什么值得做、怎样指挥各个 agent”的导演。
- 这也是他对 LLM 知识库项目感兴趣的原因：当同一份信息被从不同角度重新整理、提问和重构时，人类的理解会被增强，而不是被绕过。

### 8. 尾声：下一代 agent-native 基础设施
- 他对当前基础设施最不满意的一点是，几乎所有文档仍然主要写给人看，而不是写给 agent 看。
- 他不想再被告知“打开某个 URL、点击某个菜单”，而是希望系统告诉他“把什么 prompt 复制给 agent”。
- 在他眼里，判断某套基础设施是否真正 agent-native 的标准，是它能不能让一个 prompt 直接把应用构建并部署出去，而不是还要人类手动配 DNS、点设置页面。
- 更远期的预测则更激进：神经网络式计算机会逐步上升为主处理器，传统 CPU 更像协处理器，虽然这个过渡不会一夜完成。

## Key Takeaways
- Karpathy 说的“变化”不是 vibe coding 这个词本身，而是模型质量在 2025 年底左右跨过了信任阈值，让连续的 agent 工作流第一次真的开始跑通。
- Software 3.0 的真正含义不是“大家都去写 prompt”，而是提示词和上下文窗口已经开始承担过去脚本、流程胶水和部分应用层的职责。
- MenuGen 的例子说明，新范式不只是更快生成旧应用，而是会直接吞掉原本存在的中间应用层。
- “锯齿状能力”不是偶然 bug，而是训练机制造成的结构性现象：可验证的任务更容易被 RL 强化，不可验证的领域则仍会暴露怪异缺陷。
- vibe coding 解决的是“让更多人能做出来”，agentic engineering 解决的是“在不降低质量标准下跑得更快”，两者不能混为一谈。
- 在 agent 时代真正升值的人类能力，不是死记 API，而是对数据模型、系统边界、异常场景和抽象质量的判断力。
- “鬼魂”模型提醒使用者不要把 LLM 误当成有动机的生物；准确心智模型本身就是一种生产力。
- 最后那条底线最重要：你可以把部分思考外包给 agent，但你不能把理解力外包出去，否则你连该让它做什么都说不清。

## Insights
- 这篇对谈把“coding agent 为什么还需要资深工程师”回答得很具体：因为最贵的问题已经从写实现迁移到了定义正确抽象、识别隐性 bug 和维持质量边界。
- Karpathy 用可验证性解释 jaggedness，很适合作为 agent 选型原则：不要先问“模型是不是足够聪明”，先问“这个任务能不能被明确验证”。
- 他对 agent-native 基础设施的要求，本质上是在推动所有开发工具从 human-first UI 转成 prompt-first interface。
- 这篇文章也暗示了一个新的教育重点：未来入门者更该学系统原理、建模判断和监督能力，而不是把全部时间花在记忆库函数细节上。
