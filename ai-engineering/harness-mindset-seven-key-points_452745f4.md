## Executive Summary
网易有道 CEO 周枫从行业分享与内部实战出发，系统阐述"Harness 即产品"的观点：Agent = Model + Harness，模型只完成约 20% 的工作，让产品持续可靠运行的 80% 基础是模型之外的整层工程——上下文管理、工具、记忆、持久化状态、评测、循环控制、可观测性与权限治理。文章提出构建 Harness 产品的七个要点，覆盖产品定位（面向下一代模型设计、聚焦高智能场景）、成本观（舍得花 token 但要可核算）、工程核心（上下文工程是心脏、工具是给模型看的界面、评测驱动开发、默认单 Agent）。适合正在做大模型应用的产品与工程团队阅读，核心结论是：模型是可更换的引擎，Harness 才是你自己造的车。

3. **要做高智能产品** — 用"资深员工才能处理的复杂任务切片"筛选值得投入的场景。

5. **把上下文工程当成主任务** — 上下文管理是 Harness 的心脏，要分层管理。
6. **工具是给模型看的产品界面** — 工具设计是"模型可消费的能力单元"，不是普通 API。
7. **用评测驱动开发** — 用量化评测体系替代"凭感觉"的打地鼠式调优。

## Section Summaries

### 1. 概念界定：Harness 即产品
- Harness（马具/载体）指模型之外、把模型包装成可用产品的那一整层工程：上下文管理、工具、记忆、持久化状态、评测、循环控制、可观测性与权限治理。
- 标准公式：**Agent = Model + Harness**——模型负责"思考"，Harness 负责让这份思考可理解、可协作、可复现、可长期运行。
- 对复杂 Agent，模型也许只完成 20% 的工作，剩下 80% 让产品持续可靠工作的基础是 Harness。长程 Agent 对 Harness 的依赖超过对任何单个模型的依赖；更强的模型并不会自动变成更可靠的 Agent 服务。
- "Harness 即产品"的含义：团队真正在设计和迭代的产品，往往不是一个个具体功能，而是这一整层 Harness 本身。

### 2. 面向下一代模型能力设计产品
- 常见错误：围着模型今天的能力优化打磨（更准、更快、更便宜），结果产品上线不久就被新模型直接替换。
- 解法是超前定位：路线图不只问"模型今天能不能做"，更要问"半年后模型在规划、工具使用和长上下文上再上一个台阶，我们如何抓住红利"。
- 工程上：先用强模型跑出效果，再逐步尝试小模型替换。业务上：优先选择随模型智能提升而价值放大的场景——复杂决策、深度思考、跨系统调度、深入专业知识。
- 案例：Claude Code 负责人 Boris Cherny 在 Lenny's Podcast 访谈中透露，Claude Code 一开始只是小尝试，团队刻意按"模型将会变成什么样"而非"现在能做什么"设计产品——"我们其实不必再做 type-ahead 了，可以直接让 Agent 把所有代码都写出来"。这个赌注在 2025 年 5 月 Opus 4 发布时兑现。
- Cherny 的两条产品原则："别试图把模型框死"（少用僵硬编排，多给工具和目标让模型自己想）；"押注更通用的模型"——能随模型一起变强的灵活方案，胜过为当下定制的脚手架。

### 3. 要做高智能产品
- 判断标准：靠规则、搜索和模板就能解决的问题未必值得产品化；依赖模糊判断、跨文档理解、多步骤推理和人机复杂协作的问题才适合开发大模型产品。
- 筛选视角："类比一个需要资深员工处理的复杂任务切片"——优先选的不是流量最大的场景，而是**单次任务价值最高、判断复杂度最高、人工成本最贵**的场景。
- 这类场景起步更难，但做通后用户会把它当真正的生产力工具，而不是新鲜一下的演示玩具。任务切片越难、价值越高，模型单独能交付的比例就越低——能否稳定上线恰恰取决于 Harness 建得好不好。

### 4. 有价值的 Agent 产品，往往消耗较多 tokens
- 很多团队第一直觉是"把 token 用量压到最低"，对真正困难的任务这是一上来就设错了优化目标。高价值场景中 token 消耗是创造价值的，一定范围内越多越好。
- 正常量级：一个 Agent 任务跑下来，累计输入 token 在**数十万到数百万之间**都属正常。
- Harness 的重要任务是让 token 花费**经济上可核算**——能统计和优化消耗，该花的地方花充分、不该花的地方足够节省，如同增长团队必须量化 ROI 一样是基本功。
- 具体杠杆：① 提示词缓存（prompt caching）是优化要点；② 分层与路由——强模型跑通后把简单节点下放小模型；③ 批处理（batch）跑可异步任务、必要时做上下文重置。这些手段省的是无谓浪费，高价值环节应放开手脚花。

### 5. 把上下文工程当成主任务
- 上下文工程的目的：让模型在某一时刻究竟知道什么、不知道什么、记住什么、遗忘什么——而不是写更长更巧妙的提示词。
- "如果说 Harness 有一个心脏，那就是上下文管理"：前面几点最终都落到管理上下文内容这个动作，而非简单沿用不断积累对话上下文的默认规则。
- 至少要把上下文拆成几层：**系统规则、当前任务、检索知识、用户历史、长期偏好、工具结果**，不同层有不同的优先级、生命周期和压缩方式。
- Anthropic 对上下文工程目标的概括：找到"能最大化达成目标的、最小的一组高信号 token"，因为上下文是一种边际收益递减的有限资源。

### 6. 工具是给模型看的产品界面
- Agent 调不好工具，往往不是模型不聪明，而是工具设计得不对。国内外主流模型的 Agent 能力已较强，上下文工程之后，工具设计是团队应聚焦的点。
- 观念升级：不是写一个 API 给自己的前端调用，而是设计一个"**模型可消费的能力单元**"。工具过多、命名相似、参数含糊 → 模型误选；返回结果冗长且噪音大 → 污染上下文。
- 实用做法：① 收敛工具数量，把高频业务动作做成少数高信号、强约束的工具；② 严格 schema 和结构化输出，避免自由文本在节点间传递错误指令；③ 为关键工具写清"什么时候该用、什么时候不该用、成功与失败分别长什么样"。
- Anthropic 工具使用文档强调：影响调用效果最重要的因素之一是工具描述本身。一线经验：工具超过二十来个，模型就容易在相似工具间选错（如"订单查询"和"物流查询"搞混）；避免"瑞士军刀式"多功能工具，改用单一职责、强 schema 的小工具，调用前先做参数校验、把错误直接"回吐"给模型修正。

### 7. 用评测驱动开发
- 常见坑：做出"差不多"能工作的产品后靠手工反复调整，按下葫芦浮起瓢，陷入打地鼠困境——缺的是量化评测。
- 可上线的 Agent 必须有细分任务级的量化评测体系，至少覆盖四层：**最终答案质量、工具调用正确率、流程完成率、安全样本通过率**；更进一步还应有边界样本、对抗样本和真实线上日志回灌。
- "一定要把'凭感觉'换成'看数据'。" 实操参考：Anthropic《Demystifying Evals for AI Agents》被作者称为目前最权威的 Harness/Agent 评测指南，另有多个开源评测框架可选。

### 8. 默认从单 Agent 开始
- 多 Agent 看上去像"组织协作"令人兴奋，但有经验的团队都建议先把单 Agent 做到极致；只有当 prompt 逻辑过于复杂、工具集合拥挤、权限等级不同、任务目标天然分离时再拆。
- 多 Agent 的代价：handoff、状态同步、权限分层、成本叠加和调试复杂度。值得拆的是边界清楚且目标不同的角色，如"分诊—执行—质检""检索—分析—操作""客服—退款—物流"。
- 社区代表性争论：Cognition（Devin 团队）《Don't Build Multi-Agents》主张默认单 Agent——多 Agent 难以共享完整上下文、容易决策冲突，对"写"类强一致性任务（如写代码）尤其脆弱；Anthropic《How we built our multi-agent research system》给出反例——在"读"类开放式研究任务上，主从式（orchestrator-worker）多智能体比单个 Claude Opus 4 高出 **90.2%**，但 token 消耗约为普通对话的 **15 倍**。
- 两边指向同一条分界线：**任务偏"读"还是偏"写"、能不能共享上下文，决定该不该拆。**

### 9. 小结：你迭代的产品，就是 Harness
- 七点是同一个工程的七个侧面：超前定位定方向、高智能场景定取舍、舍得花 token 求价值、上下文管理是心脏、工具是手、评测是免疫系统、循环编排是骨架。
- 模型会一代代变强，但更强的模型不会自动变成更可靠的 Agent 服务；从 demo 到完整产品的鸿沟，始终要靠 Harness 来填。

> 模型是可更换的引擎，Harness 才是你自己造的车。

## Key Takeaways
- Agent = Model + Harness：模型约占 20% 工作量，Harness（上下文管理、工具、记忆、评测、循环控制、可观测性、权限治理）占 80%，是团队真正迭代的产品。
- 按"模型半年后会变成什么样"设计产品——Claude Code 团队放弃 type-ahead 直接押注 Agent 写全部代码，2025 年 5 月 Opus 4 发布时兑现。
- 场景筛选标准不是流量最大，而是"资深员工才能处理的复杂任务切片"：单次任务价值最高、判断最复杂、人工成本最贵。
- 高价值 Agent 任务单次消耗数十万～数百万输入 token 属正常；优化目标不是最小化 token，而是让花费可核算——杠杆为提示词缓存、强/小模型分层路由、批处理。
- 上下文至少拆六层（系统规则/当前任务/检索知识/用户历史/长期偏好/工具结果），各层不同优先级、生命周期与压缩方式；目标是 Anthropic 说的"最大化达成目标的最小高信号 token 集"。
- 工具是"模型可消费的能力单元"：超过约 20 个工具模型就易选错（如混淆"订单查询"与"物流查询"）；用单一职责+强 schema 小工具替代瑞士军刀式工具，错误直接回吐给模型修正。
- 评测至少四层（答案质量、工具调用正确率、流程完成率、安全通过率），加边界/对抗样本与线上日志回灌；参考 Anthropic《Demystifying Evals for AI Agents》。
- 单 Agent 优先：Cognition 主张"写"类强一致性任务（写代码）不拆；Anthropic 实证"读"类研究任务拆分可 +90.2% 但花 15 倍 token——按读/写与上下文可共享性决定架构。

## Insights
- 文章把 Cognition 与 Anthropic 的多 Agent 争论收敛成一条可操作的分界线（读/写 + 上下文共享），比"多 Agent 好不好"的站队更有工程价值。
- "token 花费可核算性"把成本问题从工程优化上升为组织基本功——类比增长团队的 ROI 量化，意味着 Harness 需要内建 token 计量与归因能力。
- 七个要点相互咬合：超前定位（要点1）决定了必须选高智能场景（要点2），高智能场景必然费 token（要点3），费 token 逼出上下文分层（要点4）——这是一个体系而非清单。
- "工具是给模型看的产品界面"提示了一个新角色分工：工具的 schema、描述、错误信息设计本质上是面向模型的 UX 设计。
