### Notes Column

**为什么先摸再补**

没摸清就直接补，AI 默认会按通用代码质量标准给你列 200 条测试（每个 controller、每个 service、每个 util 都要测）。看起来都合理，但根本补不完，最后要么补到怀疑人生，要么放弃整件事。

老项目改造的目标不是"达到 80% 覆盖率"，是"**改造路径上的关键节点都有兜底**"。这两个目标差别巨大：
- 通用目标（覆盖率）→ 补到死，改造迟迟动不了
- 改造目标（关键路径）→ 聚焦可控，让改造启动

**验证债背景**

Sonar 数据：96% 的开发者不完全信任 AI 输出，但只有 48% 每次都 review。这 48% 的差距叫"验证债"。老项目测试少，AI 改完没人能验证——这是老项目改造最大的隐患。

**四步摸底法**

**Step 1 — 摸核心链路（产出 docs/critical-paths.md）**

提示词要求：
- 总数不超过 **8 条**，宁少勿多
- 必须是"改造时容易出问题"的链路，不是所有链路
- 每条写：链路名、起点（哪个接口）、关键节点（哪些 service/DB 操作）、终点（什么状态算成功）

Review 重点：Spring AI Alibaba Admin 的核心链路应包括登录、Prompt 创建和运行、Dataset 创建和导入、Evaluator 跑批、实验执行、Trace 写入。账号详情查询、Trace 列表分页不算核心。起点和终点必须明确（"POST /console/v1/auth/login → 校验密码 → 写入 Token → 返回 200 + accessToken"），而非含糊的"用户登录后做事"。

**Step 2 — 摸现有测试（产出 docs/test-status.md）**

提示词约束：
- 单元测试/集成测试/E2E 各多少文件
- 哪些 Controller/Service 有测试，哪些没有
- 不要给覆盖率百分比（那是 JaCoCo 干的事）
- 对照 critical-paths.md，标出每条核心链路的覆盖情况（有/部分/没有）

Review 重点：**AI 容易把"有测试文件"等同于"链路被覆盖"**——`PromptControllerTest.java` 存在不代表 Prompt 创建链路被测了，可能只测了一个简单 GET 接口。必须按链路验证，不是按文件验证。

**Step 3 — 跑一遍看实际状态（追加到 docs/test-status.md）**

跑 `mvn test`，统计通过/失败/跳过。失败分类：代码 bug / 测试本身坏了 / 环境问题。最后给测试健康度判断：

| 健康度 | 条件 |
|---|---|
| 绿 | 90% 以上通过 |
| 黄 | 60-90% 通过 |
| 红 | 低于 60% 通过 |

Review 重点：AI 容易把所有失败都归为"环境问题"，要追问"代码 bug 类型有几个？具体是哪些？"。**跳过的也要算进健康度**，"大多数通过"但跳过 30%+失败 10% 的实际是黄或红。

**Step 4 — 算出缺口清单（产出 docs/test-gaps.md）**

提示词严格约束：
- 总数不超过 **20 项**，宁少勿多
- 只列核心链路上的缺口，不在主链路上的不列
- 每项标 **P0**（改造前必须有）/ **P1**（有了更好）
- 追求"关键路径有兜底"而非覆盖率指标
- 每项写：场景描述、为什么必须、建议测试类型

Review 重点：P0 数量控制在 5-10 个（超了就让 AI 再砍，"哪几个改造中补也来得及"）。P0 必须能直接回答"如果不补这个，AI 改了什么我会发现不了"。P1 不超过 10 个。

**三条"约束 AI 不要大而全"的原则**

这是本讲最重要的工程实践：

1. **数量上限**：每个产出文件明确写"不超过 X 项"。看到具体数字，AI 真的会去筛选。
2. **关联核心路径**："不在主链路上的不要列"这句必须写进提示词，否则 AI 按通用代码质量标准列每个 util 函数的边界测试。
3. **优先级强制分层**：P0/P1 必须分开列，混在一起 AI 会把"建议补的"和"必须补的"搅成一锅粥，让你无从下手。

### Summary

本讲核心主张：改造前先摸清测试现状，而非直接补测试。四步法（摸核心链路 → 摸现有测试 → 跑一遍看实际状态 → 算出缺口清单）让"应该测什么"和"现在测了什么"之间的差距一目了然。全程必须严格约束 AI 不要大而全——数量上限、关联核心路径、优先级分层，三条原则把 200 项清单压到 5-10 个 P0 可执行缺口。摸清比补全重要十倍。

## Key Takeaways

- **摸清 > 补全**：没摸清就补，AI 给 200 条你根本补不完；摸清了，P0 只有 5-10 条，可执行。
- **按链路验证，不按文件验证**：测试文件存在 ≠ 链路被覆盖；AI 容易混淆，必须强制按链路逐一标记。
- **测试健康度要算跳过**：跳过的测试同样是风险，不能因为"没失败"就算绿。48% 的开发者每次都 review AI 输出（Sonar 数据），另外 52% 积累的是验证债。
- **三条约束缺一不可**：数量上限 + 关联核心路径 + 优先级分层，少任何一条 AI 都会大而全反噬。
- **P0 的判断标准**：能直接回答"如果不补这个，AI 改坏了我发现不了"——回答不了的不是 P0。
- **核心链路要限 8 条**：Spring AI Alibaba Admin 的核心是登录/Prompt/Dataset/Evaluator/实验执行/Trace，账号详情查询不算核心。
