### Notes Column

**前端改造流程（四步节奏）**

前端改造没有 `mvn test` 这种自动化兜底，唯一验证方式是亲眼看效果。节奏是：
1. 起服务看现状（跑 `deps-start.sh`，AI 顺手调起后端和前端）
2. 让 AI 告诉你改造在前端哪里（"菜单路径 + UI 位置"）
3. 让 AI 改完前端（对齐 18 讲方案里 P07-P10）
4. 预览效果（勾选两个版本 → 点新按钮 → 观察 loading → modal 弹出 → 行级 diff 正常）

一个小技巧：不知道默认账号密码直接问 AI，AI 扫数据库初始化脚本告知 `saa / 123456`，比翻 README 快十倍。

**前端改造完成后的实际状态**

后端改了两件事：
- 新增 `/api/prompt/version/diff` 接口，把"两次单版本请求 + 前端拼装 diff"改为"后端统一返回 diff 结果"
- 前端 `getDiffVersion` 调新接口，`VersionCompareModal` 数据来源改为后端返回

验证效果通过，从 17 讲拆需求到 20 讲前端跑通，改造闭环跑完——直到 Robert 出于习惯又点了点页面。

**翻车：功能本来就存在**

页面上**已经有一个对比按钮**，点开弹窗里版本对比 diff 渲染得清清楚楚。这个功能早就在前端实现了：
- `version-history.jsx` 已有对比按钮
- 点击后前端并行调两次 `getPromptVersion` 拿完整数据
- 浏览器里做字符串 diff
- 渲染到 `VersionCompareModal`

整个流程完全在前端，零后端 diff 接口。

**翻车路径复盘**

| 讲次 | AI 做了什么 | 漏掉了什么 |
|---|---|---|
| 第 17 讲 | 扫 `docs/api-list.md`，没有 diff 接口，回答"没有版本对比功能" | `api-list.md` 描述的是接口，不是前端功能 |
| 第 18 讲 | 扫前端代码，识别 `VersionCompareModal` 已存在 | 默认这是"配套接口的某个组件"，没主动说"这个组件已经在工作" |
| 第 19-20 讲 | 跑通后端接口 + 前端改造 | — |
| 改造后 | — | 现在版本历史页面有两个对比按钮，用户看到会懵 |

**这次翻车说明三件事**

**1. AI 扫代码强，理解业务功能弱**

AI 可以列出所有文件、方法、调用关系，但理解不了"这个组件正在工作、用户每天都在用"这种业务事实。它看到 `VersionCompareModal.jsx` 存在，会默认这是"某个未完成的代码骨架"。它永远不会主动建议"打开浏览器点一下看看现状"——这个动作只能人来。

**2. 改造前的兜底动作是"自己点几下产品"，不是"让 AI 扫代码"**

如果 17 讲拆需求之前，打开浏览器、点几下版本历史、发现"对比"按钮已经能用，整个 17-20 讲的工作量归零。这一步只需要 30 秒。没做这一步的原因：在跟着课程节奏走，在按"先拆需求"的标准流程走，把"理解项目"这件事完全交给 AI 了——当了甩手掌柜。

**3. 人是最后的兜底员（新原则）**

整门课的原则"AI 当调研员、人当决策员"，这次翻车补充了第三条：**人不只是决策员，还是兜底员**。AI 把代码层面的事扫得再细，也替代不了"看一眼就知道"的业务判断：

> - 这个功能用户在不在用？打开生产环境看 PV 就知道。
> - 这个接口有没有客户依赖？看监控调用方就知道。
> - 这个 bug 是不是影响业务？问一下客服就知道。

**落地动作：CLAUDE.md 新约束**

```
## 老项目改造前必须做的兜底动作
任何改造任务开始之前，**先打开生产/测试环境点几下，确认要做的功能
不存在**。AI 扫代码无法发现"已存在的功能"，必须人手验证。
```

这条写进 CLAUDE.md 后，下次类似改造时 AI 会主动提醒先点产品，这次踩的坑变成了下次的护栏。

**这次改造白做了吗？**

从教学角度没有白做：目标是掌握老项目改造全流程，不是学会加某个功能。意外的是收获了一条宝贵的踩坑经验，并将其落地为可被未来执行的 CLAUDE.md 约束。

### Summary

前端改造流程本身简洁（4 步），但这一讲真正的价值在翻车复盘：整个 17-20 讲的改造实际上是不必要的，因为功能早已在前端存在。根因是把"理解项目现状"这件事完全交给了 AI 扫代码，而 AI 能识别代码文件但无法判断"这个组件正在被用户使用"。兜底动作只需要 30 秒：改造前打开浏览器点几下，确认要做的功能不存在。这条教训以 CLAUDE.md 约束的形式沉淀，成为所有后续改造的护栏。

## Key Takeaways
- **功能存在性验证是改造前的 30 秒兜底**：打开浏览器点几下，成本极低，但 AI 扫代码永远替代不了这个动作
- **AI 扫代码 ≠ 理解功能是否在用**：AI 看到组件存在默认是"未完成骨架"，不会主动说"这个在工作"
- **`api-list.md` 不能替代实际点产品**：17 讲扫 API 列表得出"没有 diff 接口"是正确的，但这不等于"功能不存在"——前端自己实现的功能不需要后端接口
- **教训必须写进 CLAUDE.md 才能成为护栏**：写进记忆会忘，写进 CLAUDE.md 每次相关改造时 AI 会主动提醒
- **老项目改造里"甩手掌柜"的代价**：把"理解项目"完全交给 AI，结果是 3-4 小时做了不需要做的事

> [!example]- 💡 答案指南（做完再看）
>
> **题目 1 - 引导答案思路：**
> 推理链条有漏洞：`api-list.md` 描述的是后端 API 接口，"没有 diff 接口"是正确的，但这不等于"功能不存在"。`version-history.jsx` 的对比功能是纯前端实现——调两次 `getPromptVersion` 拿数据，浏览器里做字符串 diff，完全不需要专用后端接口。用"API 列表"来判断"功能是否存在"是一个假设，这个假设在前端可以自己实现 diff 的场景下是错的。
>
> ---
>
> **题目 2 - 引导答案思路：**
> 具体动作：改造任务开始之前，打开生产/测试环境，按照需求描述的功能路径点几下，确认功能不存在或者存在但有问题。只需要 30 秒。AI 做不到的原因：AI 只能访问代码文件和文档，无法打开浏览器；更根本的是，AI 无法理解"某个组件正在被用户使用中"这种业务事实——它看到 `VersionCompareModal.jsx` 存在，默认的解读是"可能是某个未完成骨架"，而不是"这是每天有用户使用的功能"。
>
> ---
>
> **题目 3 - 引导答案思路：**
> CLAUDE.md 是每次 Claude Code 会话都会加载的上下文文件，写进 CLAUDE.md 的约束会在未来所有相关改造中被 AI 主动应用。HANDOFF.md 是当前任务的交接文档，下次不同任务不会读到。README 是项目介绍，不是 AI 操作约束。只有写进 CLAUDE.md 的内容，才能在未来"你可能不记得这次踩坑"的情况下，通过 AI 的自动提醒发挥护栏作用。这就是"docs/ 活资产"的价值：坑踩一次，护栏永久生效。
