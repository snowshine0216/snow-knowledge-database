### Notes Column

**课程定位**

这是方法论基础模块（共5讲）的第一讲。目标不是教工具用法，而是建立认知底座：AI协作心智 + 工具地图 + 判断力框架。

**真实场景**

Leader 丢给你一个 Java + Spring Boot + MyBatis 老项目 `xxx-scheduler`，原维护者老张已离职，README 只有几行部署命令，代码里散落着 `// 不要删，某某对接方需要` 等无法追溯的注释。一下午过去了，一行代码都没写——这才是老项目改造的真实起点。

**九步原始链路**

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 找人聊（列疑点清单，问同事/产品/架构师/运维） | 获取代码外的隐性知识 |
| 2 | 翻所有资料（README、wiki、Confluence、企微历史群） | 建立整体感 |
| 3 | Clone 项目，浏览代码结构 | 画粗糙地图 |
| 4 | 搭开发环境，把项目跑起来 | 建立可观察基线 |
| 5 | curl 访问核心接口 | 验证项目跑通 |
| 6 | 带疑点深挖代码 | 逐一回答"未知"标记 |
| 7 | 画出核心链路（手绘 Mermaid） | 让项目在脑子里立起来 |
| 8 | 小步动手改造 | 每改一处验证副作用 |
| 9 | 验收（curl + 相关业务场景 + review） | 确认改造完成 |

**70/30 比例**

前六步（了解）占 70% 时间，后三步（改造）占 30%。这与"拿到项目马上写代码"的直觉相反。做得稳的工程师反而在理解上花更多时间。

**AI 进来后的分工变化**

AI 加速的是信息密度低的步骤：读 README 出摘要、扫仓库出 Mermaid 架构图、梳理接口清单。但 AI 覆盖不了：
- "某某对接方是谁"（代码里没写）
- "这段逻辑删了会出什么事"（只能猜，不能承担责任）
- "这个改造要不要上线"（决策权在人）

**跳过前六步的典型失败路径**

拿到项目 → 贴一段代码问 Claude Code "这项目是干什么的" → 得到浅层认知 → 直接让 AI 改代码 → 看起来跑通了 → 上线炸了（触发 `// 不要删` 的隐性约定）。问题不在 AI，在于传递给 AI 的上下文是空的。

**冷启动心理预期**

前六步可能花一到两天甚至两周，感觉什么都没产出。但这是投资不是浪费。飞轮转起来后：第一个改造任务磨两三天，第二个一天，第三个几小时。老项目改造的核心心法：**熬过冷启动**。

### Summary

老项目改造有一条九步原始链路，前六步是"了解"（70%时间），后三步是"改造"（30%时间）。AI 没有推翻这条链路，只是重新分配了每一步的人机分工——信息密度低的步骤可以让 AI 主导，但代码之外的隐性知识、最终决策权永远在人。跳过前六步直接让 AI 改代码，本质上是给 AI 一个空的上下文，这是大多数人用 Claude Code 用得不顺的根源。

## Key Takeaways
- **九步链路**：了解项目（找人聊→翻资料→浏览代码→搭环境→访接口→深挖）+ 改造（动手→验收），缺一步都是债。
- **70/30 原则**：70% 时间理解、30% 时间动手——和"马上写代码"的直觉相反，但决定了改造是否稳定。
- **AI 的上下文边界**：AI 能把读 README、画架构图、梳接口的速度压缩到分钟级，但"// 不要删，某某对接方需要"背后的意义永远需要人去追。
- **冷启动是投资**：前期理解阶段看不到产出但积累的文档和心智模型，会在后续改造中以复利形式回报。
- **跳过前六步的代价**：给 AI 空上下文 → AI 给出脱离项目实际的方案 → 上线炸了 → 怪 AI 不靠谱（实为用法错误）。

> **题目 2 - 引导答案思路：**
> 代码里有条注释 `// 不要删，某某对接方需要`，AI 读不出这句话背后意味着什么（某个真实的对接方依赖这段逻辑）。若工程师跳过"找人聊"步骤直接让 AI 改代码，AI 可能按"最佳实践"删掉看起来多余的代码，导致上线后对接方报错。问题不在 AI 能力，在于传递给 AI 的上下文缺少了代码之外的隐性知识。
>
> ---
>
> **题目 3 - 引导答案思路：**
> 冷启动阶段（前六步）可能持续一两天甚至两周，期间没有明显产出，容易让工程师感到焦虑。作者建议把这段时间视为"投资而非浪费"——理解越深，后续改造越轻松；文档积累越厚，AI 协作越准确；飞轮一旦转起来，第一个任务两三天，第二个一天，第三个几小时，这是复利效应的体现。
