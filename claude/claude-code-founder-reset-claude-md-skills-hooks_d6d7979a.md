# Claude Code之父：每半年清空一次claude.md、skills和hooks，模型自己会想办法

## Executive Summary
InfoQ 将一场 Boris Cherny 与 Diana 的播客译为六段访谈。主张不是“永远不用 CLAUDE.md、Skills 和 Hooks”，而是每当模型代际变化时，先用删除与消融实验重新证明哪些指令、工具和 Harness 仍然必要；文中称 Opus 5 发布后，Claude Code 团队一次删除了超过 80% 的系统提示词。文章进一步把高效使用模型归结为经验实验：给稍有难度的目标、约束和退出标准，提供可验证结果的环境，再依据真实失败才补充提示词、Skill 或 MCP。它同时列出长程运行、提示词注入防护、Bun Zig→Rust 重写、Electron→Swift 实验、Dynamic Workflows 和 Routines 等案例，但这些均是访谈转述，而非可直接当作公开产品承诺的规格。

## Section Summaries

### 1. 不依赖 Goal 命令，Opus 5 可连续运行数月
访谈称，Opus 5 与 Auto Mode 结合后可连续运行数天、数周甚至数月，而不必额外依赖 Goal 命令或其他脚手架；模型会持续朝任务完成推进。文章也转述一套提示词注入防护：约三年的对齐研究、提示词注入分类器，以及 Auto Mode 分类器共同组成三层防护；其中“直接观察神经元激活”的机制解释性说法归因于 Crysola 研究。主持人提到 ARC-AGI-3 达 **30%**，但文中没有给出基准设置或原始结果链接。

### 2. 每隔六个月按一次删除键
文章的操作建议是把系统提示词、工具提示词、CLAUDE.md、Skills 与 Hooks 当作针对特定模型版本的假设，而非永久资产。Boris 称 Claude Code 在 Opus 5 发布后删除了超过 **80%** 的系统提示词：先清空，再逐行加回，用消融实验确定每一项是否仍然带来可观收益。文中还提到可用 `--system-prompt` 做替换实验，以及一个未正式写入文档、以 `CLAUDE_CODE_SIMPLE=1` 之类环境变量移除系统/工具提示词的 Simple Mode；两项均应视为转述线索，使用前需要核对当前官方文档。

对个人工作流，文章不建议预先猜测模型需要什么指导，而是先让它在真实代码库运行；只有某种失败反复发生时，再把最小化的指令加回。其含义是：每条长期指令都会在每轮被重新读取，既有维护成本，也可能在新模型上约束已有能力。

### 3. 当一切都在快速过期，什么才是稳定的？
访谈认为评测一般比 Harness 更耐用，但也只可能跨一到三代模型：当模型把题做满，就需要根据真实困难重新设计。文章用 **hobbling** 描述产品设计反而阻碍模型本可完成的任务，用 **product overhang** 描述模型已有能力却没有产品把它诱导出来的状态。Claude Code 的早期例子是：当时的 Sonnet 3.5 已可能写整个文件，但市场产品仍以单行/多行补全或只读聊天为主；给模型终端与写入权限、采用更简单的 Harness，才使这种能力被产品释放。

文章因此建议，将任务描述提升到目标、约束和退出标准的层级，避免把人工步骤逐条规定死；模型真正需要的是能够尝试的难题和判断结果对错的反馈。Bun 的案例按文中说法为：模型借助 Dynamic Workflows 在 **11 天**内把超过 **10 万行**的 Bun 代码库从 Zig 重写为 Rust，并依赖 Bun 与 Node.js 的测试套件验收；这一案例可与 [[bun-rewrite-zig-to-rust-with-claude-code]] 对照阅读。

### 4. 数千个智能体跑了两周，要把 Electron 桌面端重写成 Swift
文中将“提示词工程”的重点转为“选择略高于当前能力边界的任务，并给出验证路径”。Boris 的示例是：先给 Claude Tag 接入 GitHub 上的 macOS Runner 和一个空仓库，再要求其把 Electron 版 Claude 桌面应用重写为 Swift，在 Mac 虚拟机运行两版应用、截图并逐像素比较，未完成前不要停止。按访谈时点，任务已运行 **14–15 天**，模型还自行在 Slack 频道按几分钟间隔发送进度截图。

这个案例的重点不是一条“神奇提示词”，而是验证环境：访问代码库、能启动 Mac 虚拟机、能截屏比较、能持续报告进度。文章明确称 `/go`、`/loop` 等机制可能有帮助，但不是长程任务的充分条件；若无法检验产物，模型容易卡住或误判完成。

### 5. 数千个智能体怎么启动？
文章区分两类编排。Dynamic Workflows 面向一个可分解的复杂目标：在 Bun Runtime 沙箱和虚拟机中，模型可按阶段启动几十、数百或数千个智能体，后续批次负责验证或总结前一批的结果；文中把这种组合称为“智能体代数”，并将其描述为增加测试时计算的方式。Loops/Routines 则面向重复任务：Loop 在本地以 Cron Job 方式执行，Routine 在云端执行，运行之间不共享上下文但可能共享记忆。

作为内部维护实例，文章称团队在 CLI、iOS、Android 与桌面代码库使用例程：每日用静态与动态分析清理死代码、移除已覆盖 **100%** 用户的实验开关、补测试覆盖、删除无用测试，以及寻找重复抽象的“抽象警察”。文中称每日约有 **20–30** 个此类 Routines 运行；这应作为访谈中的组织实践，而非默认适用于所有仓库的配置建议。

### 6. 当编程逐渐被解决，什么能力真正拉开差距？
Boris 为“编程已经被解决”加了范围限制：深层系统代码、分布式系统与像素级 UI 验证仍然困难，视觉和计算机操作虽有进步但不完美。文章认为，在更多常规编码任务中，人类的差异化会转向经验主义——放下“旧模型做不到”的先入判断，实际试运行新模型，再以失败为依据调整流程。

对学习者，访谈不是主张放弃计算机科学，而是强调把硬技能与实际问题、产品、设计判断、数据科学和用户交流结合。Boris 用自己从 TI-83、BASIC 到汇编的早期学习经历说明，学习技术最好有具体要解决的问题；其中涉及考试作弊的个人轶事仅作原文记录，不构成建议。

## Key Takeaways
- **先删后加是可检验的配置迁移法**：面对新模型，先删除系统提示词、`CLAUDE.md`、Skills 或 Hooks，再依据重复失败逐项恢复，比把旧补丁原样叠加更容易发现约束是否已过期。
- **每条指令都应有失败证据**：文章建议在真实代码库中观察模型；只有同一错误重复出现，才加入最小指令，因为系统/项目提示会在每轮被重新读取。
- **验证工具比提示词花样更关键**：Electron→Swift 案例把 macOS Runner、双版本运行、截图和逐像素比对连接成验收闭环；没有该闭环，“持续执行”无法可靠地等于“完成”。
- **评测不是永久资产**：当评测被一到三代模型做满，应从最新失败模式重新构造；Bun 重写案例之所以可验收，依赖已有的 Bun 与 Node.js 测试体系。
- **多智能体需要任务语义的分流**：Dynamic Workflows 用于阶段化分解的复杂目标；Loops/Routines 用于每日死代码、实验开关或测试维护等重复动作，二者不是同一种并行化。
- **“编程已解决”有边界**：原文仍将分布式系统、深层系统代码和 1 像素级 UI 验证列为困难区，不能把访谈的宏观判断外推为所有工程任务已可无人监督。

## Insights
- **把指令当成可回归测试的假设**：`CLAUDE.md`、Skill 和 Hook 最适合记录被反复观察到的失败模式；升级模型时，以删减实验衡量收益，可防止旧约束悄悄压低新模型表现。
- **高杠杆来自可审计闭环**：给模型更大自主权前，先提供测试、截图、真实环境操作和进度输出；这是把长程运行从“赌它会做完”变为“能观测地修正”的前提。
- **模型能力缺口是产品探索方法**：选择稍超出预期的任务，明确退出标准，再让模型尝试，可能找到旧产品没有暴露的能力；但发现后仍需单独验证可靠性、成本与安全性。
- **维护自动化应从低风险、可验证例程开始**：死代码扫描、测试补全或实验开关清理都要有明确判据、代码审查与回滚路径，不能仅因“可启动数千智能体”就扩大写权限。
