## Executive Summary
机器之心整理了 Anthropic 研究产品经理 Theodora（Theo）Chu 的一段演讲。核心数据是「Anthropic 内部超过 80% 的代码由 Claude 合并」——模型已从「回答问题」转向「在可反馈、可验证、可修正的环境里持续完成任务」。Theo 把这一年模型能力的跃迁拆成三个领域（先规划再行动、错误恢复与自我纠正、长上下文连贯性），并给出三条面向未来的构建战术：动态刷新 Evals、精简「脚手架」（shrink the scaffolding）、闭环智能体循环（Close the Agent Loop）。面向所有正在构建 Agent 产品的开发者——尤其是仍在用 12 个月前的任务测试今天模型的人。

## Outline
1. **一年内失败率大幅下降** — 用 SWE-bench Verified 量化模型一年来的能力跃迁，并指出旧 Evals 已开始饱和。
2. **能力增长的三个核心领域** — 先规划再行动、错误恢复与自我纠正、长任务周期连贯性。
3. **开发者该如何为未来构建** — 三条战术：刷新 Evals、精简脚手架、闭环智能体循环。

## Section Summaries

### 1. 一年内失败率大幅下降
Theo 用 SWE-bench Verified（一组真实 GitHub issue，模型需理解问题、改代码并通过测试）量化能力跃迁：一年前的 **Sonnet 3.7 得分约 60%**，到 **Opus 4.8 已达 88%**。这意味着一年前模型在这些任务上的失败次数约为现在的 **3 倍**。

关键论点不是「多做对几道题」，而是 **失败率正在快速下降**——失败率降下来后，模型才有可能承担更长、更复杂、更接近真实工作的任务。文中还指出，在最新的 **Mythos 和 Fable 系列** 模型上，该基准已出现接近饱和的迹象：过去足够难的测试今天已不再能有效区分模型能力。

> 如果你还在用 12 个月前的任务测试今天的模型，就很容易低估模型真正的能力边界。

### 2. 能力增长的三个核心领域

#### 一是先规划，再行动
同一任务「一次性重建 Claude.ai 网站」在新旧模型上表现迥异：旧模型上来就写大量代码、调用大量工具，几乎不规划，结果界面看似合理但功能不闭环。Theo 的类比：

> 有点像我装宜家家具时的样子：一上来就动手，根本不看说明书，先开始拼，拼着拼着发现做错了，然后才意识到自己应该回去看说明书。

以 Opus 4.8 为代表的新模型表现出 **自适应思考（Adaptive thinking）**：先在内部深思规范，在预先规划中及时捕捉错误（推理中会看到「实际上……」「算了，还是……」这类自我修正词）。先规划后行动让模型第一次执行就高效落地，**大幅减少不必要的工具调用与代码行数**。建议：允许模型先思考，产品体验为思考留空间，用自适应思考让模型自行判断「是否需要思考、思考多久」。

#### 二是错误恢复和自我纠正
过去做 Agent 重点在「让模型调用更多工具」，但 Theo 强调工具调用本身不够——**模型必须知道自己什么时候做错了**。旧模型的常见病是 **doom looping**：失败后即便被提示「换一种方式」，再次尝试时仍回到同样的解法。

新模型能读取反馈、理解失败原因、尝试不同路径，从被动执行转向具备错误恢复能力。这对 Agent 产品尤其关键，因为任务足够长就一定会遇到错误（代码跑不通、点击失败、测试不过、用户不满、环境异常）。

> 真正有价值的 Agent，不是永远不犯错，而是犯错之后能不能恢复。

因此要重新设计模型所处的 **环境**，让环境能给反馈。例如做应用生成 Agent，就该给它访问前端界面的能力，让它自己点击、测试、判断按钮是否可用、页面是否正常，形成「执行 → 验证 → 修正 → 再执行」。好处之一：模型不再因 doom looping 浪费 token，而是用更少 token 完成任务。

#### 三是模型越来越擅长在更长任务周期上运行
旧模型在长任务中常「跟丢主线」（Losing the plot）——做着做着忘了最初目标或核心指令。现在模型在长程任务的上下文连贯性上显著突破，能稳定将注意力维持在 **100 万 Token 甚至更高** 的级别。这意味着开发者不必把上下文切得很碎，可以直接把 **整个代码库** 递给模型；更合理的方式是把更完整的任务交给模型（整个代码库而非单个文件、完整产品需求而非孤立函数、跑完整流程而非局部步骤）。

当规划、错误恢复、长上下文三者叠加，Agent 形态发生变化：先规划→执行→通过工具或人类反馈验证→发现问题就调整计划继续执行，循环直到完成。

### 3. 开发者该如何为未来构建

#### 一是主动保持野心，动态刷新评估基准（Evals）
更大胆地让 Claude 处理更多事——不要总测试你觉得它 12 个月前就能做的任务，而要思考它「今天还做不到」的任务并持续关注。模型快速进步后最易出现的误判是「觉得新模型没明显提升」，原因往往不在模型而在 **Evals 过时**。

> 有些客户在新模型发布后会说：「我的 Evals 只提升了 1%，所以这个模型好像没强多少。」但真正用起来后，他们会发现新模型在某些能力上提升非常明显，只是原来的 Evals 根本没测到。

AI 时代的 Evals 类似单元测试，但好的 Eval 不能只测今天会做的事，还要包含「今天尚未完全解决、但未来用户体验需要」的任务——**面向未来设计**。把用户报告的最新失败模式、以及应用未来发展方向融入测试用例；遗留问题被证明不可解时，立刻换上更难的题目。

#### 二是精简「脚手架」（Shrink the Scaffolding）
「脚手架」指为修补旧模型漏洞而套上的系统提示词、外部工具、代码 Harness、各种约束和补丁（格式错了加一条规则、没遵守要求再写一段约束……）。新模型指令遵循能力变强后，**旧补丁反而会成为问题**。

Anthropic 自身案例：团队一度以为新模型在 Claude.ai 的引用功能上出了 Bug，检查后发现是新模型极其听话地执行了一行很久以前写进系统提示词、但现在已过时的引用格式指令。**最终只需删掉那行过时提示词，功能就恢复正常**。结论：应「针对意图」写简洁提示词，明确最终想要的结果，而不是围绕旧模型的失败经验过度包装。给模型松绑才能看清它真正的天花板。

#### 三是闭环设计，让模型验证自身的输出结果（Close the Agent Loop）
模型完成复杂任务，光会思考不够，还需要 **动作能力**——这是构建自改进 Agent 的核心逻辑。具体三步：

| 动作 | 含义 |
|---|---|
| 给模型留出思考与工作空间 | 引入自适应思考；产品上允许前端思考，并可用 **投入度拨盘（Effort Dial）** 上调/下调钻研程度 |
| 以受控方式开放高权限 | Claude Code 的「自动模式」分类器在「开发者控制欲」与「模型自主权」间找平衡，自动甄别安全可取的行动，防止误删环境 |
| 提供自我质检的工具 | 配备 **「Computer Use」** 等自动化验证工具，让 Agent 自己在前端点击、做质检，通过真实反馈发现错误、迭代修正代码 |

## Key Takeaways
- 模型能力跃迁的本质是 **失败率下降**（SWE-bench Verified 一年从 ~60% 到 88%，失败约为原来的 1/3），而非单纯多答对题。
- 新模型用 **自适应思考** 先规划再行动，把「重建 Claude.ai」这类任务的工具调用与代码量大幅压低（对比旧模型「不看说明书装宜家」式蛮干）。
- 旧模型的核心病是 **doom looping**——被纠正后仍回到同一错误解法；新模型能读反馈、换路径，具备真正的错误恢复。
- 长上下文连贯性达 **100 万 Token+**，开发者应「把整个代码库/完整需求/完整流程」交给模型，而不是切碎喂单文件。
- **Evals 会过时**：客户「Evals 只涨 1%」常因旧基准没测到新能力；好 Eval 要包含模型「今天还做不到」的未来任务。
- **Shrink the scaffolding**：Anthropic 删掉一行过时的系统提示词就修好了 Claude.ai 的引用「Bug」——新模型太听话会忠实执行过时补丁。
- **Close the Agent Loop** 的三件套：自适应思考 + 投入度拨盘（Effort Dial）、Claude Code 自动模式分类器（受控开放权限）、Computer Use（自我质检）。

## Insights
- 「先规划再行动」直接对应 token 经济性：减少 doom looping 与盲目工具调用 = 更少 token 完成任务，这是产品成本与可靠性的双赢，而非单纯的「质量」改进。
- 真正的工程杠杆从「给模型加约束」转向「给模型设计带反馈的环境」——让 Agent 能访问前端、自己点击测试，是闭环的前提；没有验证信号就没有错误恢复。
- 「脚手架」是技术债的一种特殊形态：它随模型代际更替由资产变为负债，因此每次模型升级都应反向审计并删除旧补丁，而非只做加法。
- 「针对意图写提示词」与「围绕历史失败打补丁」是两种相反的范式；后者在指令遵循能力提升后会主动制造回归 Bug（过时指令被忠实执行）。
- Effort Dial / 自适应思考把「思考预算」做成产品旋钮，意味着延迟与成本可按任务难度动态权衡，而非全局开关。
