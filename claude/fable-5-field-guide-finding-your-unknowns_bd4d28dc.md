## Executive Summary
这篇文章转译并介绍了 Claude Code 工程师 Thariq Shihipar 关于 Fable 5 的长博客《A Field Guide to Fable: Finding Your Unknowns》。核心观点是：强模型失败时，瓶颈往往不是“模型不够聪明”，而是用户给模型的“地图”（提示词、Skill、上下文）与真实“疆域”（代码库、现实约束、任务细节）之间存在未知项。作者把 agentic coding 拆成实现前、实现中、实现后三个阶段，分别用 blindspot pass、原型、反问、参考代码、实现计划、implementation notes、解释文档和测验来持续发现未知项。对 Claude Code 用户来说，这篇文章最有价值的部分不是某个提示词模板，而是一套把模糊意图逐步转成可执行、可审查、可学习工作流的方法。

## Section Summaries

### 1. 引言：Fable 5 与信息差
文章开头把 Fable 5 描述为一个从“AI 封神时刻”到被美国政府禁令强制下线、再到禁止非美国人访问的高关注模型。随着风波平息，作者强调模型最终要回到生产力场景，而 Claude Code 工程师 Thariq Shihipar 的博客试图回答一个常见问题：为什么模型已经很强，用户仍然觉得它“做不对任务”。

这里给出的答案是“信息差”：用户提供的提示词、Skill、上下文，与任务真正需要执行的细节之间存在差异。文章随后说明，它会附上 Thariq 的博客全文，主题是如何打破这种信息差。

### 2. 地图不等于疆域
Thariq 用“地图并不等于疆域”概括与 Fable 5 协作的经验：
- **地图**：用户交给 Claude 的任务表征，包括提示词、技能和上下文。
- **疆域**：真正发生工作的地方，包括代码库、现实世界和其中真实存在的约束。
- **未知项**：地图与疆域之间的差距。当 Claude 碰到未知项时，它必须按自己对用户意图的最佳猜测做决定。

作者认为，Fable 是第一个让他明显感觉到“工作质量瓶颈取决于澄清未知项能力”的模型。复杂任务不会因为前期计划就彻底消除不确定性；有些未知项会在实现深处出现，有些未知项甚至会指向一个结论：原方案本身可能不该继续做。

### 3. 了解你的未知项
文章用四类知识状态来拆解一次 Claude 协作：
- **已知的已知**：已经写进提示词的内容，例如“我想要什么”。
- **已知的未知**：用户知道自己没弄清楚的事。
- **未知的已知**：用户觉得显而易见所以没写下来，但看到结果后能立刻判断对错的标准。
- **未知的未知**：用户完全没考虑过的问题，或者不知道一件事可以做到多好的知识空白。

作者把优秀的 agentic programmer 描述为“未知项更少”的人：他们清楚自己想要什么，细节充分，并且与代码库和模型行为保持同步。但优秀实践不是假装没有未知项，而是预设未知项存在，并通过与 Claude 协作持续减少和提前规划它们。

### 4. 帮助 Claude 以帮助你自己
这一节强调指令粒度的平衡：
- 指令过于具体时，即便另一种方案更合理，Claude 也可能严格照做。
- 指令过于模糊时，Claude 会基于通用行业最佳实践做假设，而这些假设未必适合当前代码库或任务。

作者建议给 Claude 足够的起点上下文：当前思考到哪一步、自己对问题和代码库的熟悉程度、希望它以什么方式作为思考伙伴协作。Claude 的优势在于快速搜索代码库和互联网、掌握广泛通用知识、从失败中快速迭代；但这些能力需要被用户的真实上下文校准。

### 5. 实现前：盲点、原型、反问、参考资料、计划

#### 5.1 盲点扫描
当用户进入不熟悉模块或陌生工作类型时，容易拥有大量“未知的未知”：不知道该问什么、什么算好、历史上做过什么、哪些坑应避免。作者建议直接让 Claude 做一次 `blindspot pass`，并明确使用 `unknown unknowns` 这样的词。

文中的示例包括：
- 新增身份认证提供方，但不了解代码库里的认证模块，让 Claude 扫描相关未知项并帮助用户写出更好的提示词。
- 不懂调色但要给视频调色，让 Claude 解释调色领域的 unknown unknowns，帮助用户形成更好的表达语言。

#### 5.2 头脑风暴与原型
当任务包含很多“未知的已知”时，作者会让 Claude 先头脑风暴或做原型。视觉设计就是典型例子：用户可能无法提前精确定义好坏，但看到多个方向后能判断偏好。

文章给出三个具体提示词模式：
- 为一组数据做仪表盘时，让 Claude 生成一个 HTML 页面，提供 **4 种风格差异很大** 的设计方向。
- 在真正接线前，用假数据做一个单独 HTML 文件，模拟新的编辑器工具栏，先反馈布局再改真实应用。
- 面对“用户完成 onboarding 后流失”的粗略问题，让 Claude 搜索代码库并头脑风暴 **10 个** 可以介入的位置，从低成本到高野心方案排序。

这一节的关键不是“多做几个版本”，而是用低成本原型提前暴露那些实现后才发现会很贵的偏好和约束。

#### 5.3 反问
头脑风暴后仍有未知项时，作者会让 Claude 采访自己，而且“一次只问一个问题”。问题优先级不是按好奇心排序，而是按“用户回答是否会改变架构设计”排序。这个模式适合把模糊需求转成关键决策，而不是一次性收集大量低价值信息。

#### 5.4 参考资料
当用户无法完整描述想要什么时，最好的输入往往是参考资料，尤其是源代码。文章举例：如果 `vendor/rate-limiter` 里的 Rust crate 实现了想要的回退重试语义，就让 Claude 阅读它，并在 TypeScript API 客户端中复现同样语义。

文章还提到 Claude Design 的工作方式：不只看截图，也可以读取网站模块背后的代码，从标记结构、组件组织方式和真实构建方式中获取更丰富的细节。

#### 5.5 实现计划
准备进入实现时，作者通常会先让 Claude 产出实现计划，并把最可能需要用户修改的决策点放在前面，例如数据模型、类型接口和 UX 流程。机械性重构则放在下方，因为那部分可以更多交给 Claude 处理。

这个实践的作用是把高风险决策前置，而不是等 Claude 写完大量代码后才发现数据模型或用户流程方向错了。

### 6. 实现中：实现笔记
即便前期做了计划，未知项仍然会在实现中出现。作者建议让 Claude Code 维护一个临时的 `implementation-notes.md` 文件或 `.html` 文件，记录它在实现中做出的决策。

文中的提示词要求 Claude：如果遇到导致必须偏离原计划的边界情况，就选择保守方案，在 `Deviations` 下面记录原因，然后继续推进。这样下一轮尝试可以从真实偏差中学习，而不是只看到最终 diff。

### 7. 实现后：解释文档与测验

#### 7.1 推介与解释文档
发布结果时，作者强调不只是提交代码，还要让评审者理解、支持和批准。解释文档有两个作用：
- 当评审者也带着同样未知项时，帮助他们快速建立上下文。
- 当专家想确认常见失败点已经被考虑时，加速审批。

示例提示词是把原型、规格说明和实现笔记打包成一个可直接发到 Slack 的文档，并在开头放演示 GIF。

#### 7.2 测验
长会话结束后，Claude 可能完成了比用户意识到更多的工作。作者认为只看代码 diff 只能获得浅层理解，因为很多行为依赖既有代码路径。

因此，他会让 Claude 生成一份 HTML 报告，解释上下文、直觉、具体变更，并在底部附一份用户必须通过的测验。他只有在“完美通过测验”后才会合并代码。这个做法把代码审查从“看过 diff”提升为“能解释行为变化”。

### 8. 发布 Fable 的串联案例
作者用 Fable 发布视频说明如何串联这些方法。视频完全由 Claude Code 剪辑完成，而视频剪辑对作者来说是新领域。

他的推进路径是：
1. 从已知部分开始：知道 Claude 可以用代码编辑视频并做转录，但不确定准确度。
2. 让 Claude 解释 Whisper 类转录技术如何工作，以及是否能用 `ffmpeg` 准确剪掉“嗯”等语气词或较长停顿。
3. 想要创建一个与说话词语时间同步的 UI，但不确定可行性，于是让 Claude 使用 Remotion 和转录文本做视频原型。
4. 发现视频偏灰暗后，意识到问题是调色，但自己不理解“好调色”的标准；于是从“让 Claude 生成几个版本给我选”改成“让 Claude 教我调色”，先补齐判断标准。

这个案例展示的是同一个原则：当用户没有评价语言时，继续让模型盲目产出版本并不高效；应该先让模型帮助用户发现和命名未知项。

### 9. 结论与社群信息
文章最后回到“地图与疆域匹配”：模型越强，用户越需要用正确方法定义未知项。长周期任务失败时，常常不是要立刻要求模型重做，而是要投入更多时间定义未知项，或创建能让 Claude 在未知项中灵活应对的实现计划。

末尾的 MLNLP 社群信息说明该社区面向机器学习与自然语言处理的学生、教师、企业研究人员和爱好者，提供技术交流群加入方式。

## Key Takeaways
- 强模型的失败常常来自“地图”和“疆域”不匹配：提示词、Skill、上下文没有覆盖代码库和现实约束中的真实未知项，Claude 就只能按最佳猜测补洞。
- Fable 5 的关键启发不是“写更长提示词”，而是把实现前、实现中、实现后都变成发现未知项的过程，尤其是在复杂任务中持续校准模型对意图的理解。
- `blindspot pass` 适合进入陌生模块或陌生领域，例如新增认证 provider 或第一次做调色；用户应明确告诉 Claude 自己不了解什么，让它帮助暴露 unknown unknowns。
- 原型的价值在于提前暴露“未知的已知”：文章中用 HTML 仪表盘的 **4 种设计方向**、假数据工具栏、onboarding 流失的 **10 个介入点** 来降低后期返工成本。
- 让 Claude “一次只问一个问题”比一次性列出大量问题更适合关键需求澄清，尤其要优先询问会改变数据模型、类型接口或 UX 流程的答案。
- 参考代码比抽象描述更强：文中 `vendor/rate-limiter` 的 Rust crate 示例说明，即使跨语言，Claude 也能从真实实现中迁移回退重试语义到 TypeScript API 客户端。
- `implementation-notes.md` 是把实现中偏离计划的原因显性化的低成本机制，特别适合记录边界情况、保守选择和 `Deviations`。
- 合并前测验把“我看了 diff”变成“我能解释行为变化”：作者会让 Claude 生成 HTML 报告和测验，并在完美通过后才合并。
- Fable 发布视频案例串起了 Whisper、`ffmpeg`、Remotion 和调色学习，说明当用户缺少评价标准时，应先让 Claude 教会自己判断，而不是只让它继续生成候选版本。

## Insights
- 对 agentic coding 来说，提示词质量本质上是上下文建模质量：用户越能显式说清自己知道什么、不知道什么、看到后才知道什么，模型越少需要猜测。
- 实现计划最有价值的部分不是任务列表，而是把可逆性最低的决策放到最前面，例如数据模型、类型接口、用户可见文案和 UX 流程。
- HTML 在这篇文章中反复出现，不只是展示格式，而是一种低成本反馈介质：设计方向、工具栏原型、解释文档、变更测验都可以用 HTML 承载。
- “让 Claude 教我领域标准”是处理陌生领域的关键动作；调色案例表明，没有评价语言时，生成更多版本只会把选择压力留给用户。
- 实现后的解释文档服务于组织协作：Slack 可转发文档、演示 GIF、规格说明和实现笔记可以帮助非实现者快速确认未知项和失败点已被处理。
